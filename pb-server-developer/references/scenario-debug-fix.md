# 场景：问题定位/修复

## 目录

- 目标

## 目标

处理报错、异常、功能不生效、页面按钮不显示、接口返回异常、SQL 报错、自动任务异常等日常问题，并用最小安全改动修复根因。

## 适用范围

- 用户提供报错堆栈、日志、截图、接口返回或现象描述。
- 已有功能行为不符合预期。
- 需要判断问题来自 JSP/JS、Controller、Service、DAO、SQL、配置、权限或数据。

## 必查项

1. 先确认目标项目、版本、模块和复现入口。
2. 保存并引用用户给出的原始报错关键行，不要凭印象改代码。
3. 查当前项目同类实现；涉及产品化/个性化时，再查 `source_code_lib/` 或匹配产品化基线。
4. 如果项目接入 GitNexus，修改目标符号前先做 impact 分析。
5. 编码前检查 Git/SVN 状态；有冲突或目标文件已有改动时先汇报。

常用搜索：

```bash
rg -n "报错关键字|接口名|按钮ID|JSP名|JOB_NAME|SQL关键表" .
rg -n "@RequestMapping|Ext.Ajax.request|url:|loadUrl|PB_SYS_BUTTON|PB_AUTO_TASK" .
```

## 定位流程

1. 从用户可见入口开始：页面/JSP/JS、接口 URL、自动任务名、SQL 脚本或配置键。
2. 顺链路定位：前端参数 → Controller mapping → Service → DAO/SQL → 配置/数据库表 → 返回结构。
3. 对比可正常工作的同类功能，优先找差异点。
4. 先验证假设，再修改代码；不要把无关重构混进 bug 修复。
5. 如果根因是数据或配置缺失，优先给 SQL/配置修复方案，并说明是否需要代码改动。

## 修复原则

- 只修本次根因，不顺手格式化、重命名或改公共接口。
- 兼容历史数据和缺省配置；业务开关默认应保持原有行为。
- 异常分支要补充有用日志，但不要打印敏感报文、密码、token 或完整文件路径。
- 对支付、凭证、清算、自动任务等核心流程，优先小范围补条件或兜底，不改变既有状态流转。

## 验证方式

- 说明复现前后变化。
- 条件允许时执行模块编译、单测或定向接口调用。
- 无法运行时，给出手工验证步骤：页面入口、按钮、请求 URL、关键参数、预期返回、需要检查的数据库记录。
- 修改完成后，如果项目规则要求 GitNexus detect_changes，先执行并总结影响范围。
