## 目标

为新页面或已有页面补齐 `loadXXX.do`、`queryXXX.do` 这类数据加载接口，让前端能拿到分页列表、详情或下拉数据。

## 适用范围

- 页面首次加载后的列表查询。
- 新表、新查询条件、新分页接口。
- 需要把数据返回给 ExtJS/MVC 列表或详情区。

这个场景只管“怎么把数据查出来”，不管菜单、模块、按钮、状态、列配置。

## 先判断哪条路

先判断目标项目里是否已经存在现成的单据引擎承载关系：

- 如果只是新加一张表，目标产品化里没有这张表的 billType / 字段映射 / 明细配置，默认走**直连查询**。
- 如果目标项目已经在同一业务域里大量使用单据引擎，并且这次也要纳入统一装载体系，再考虑**单据引擎**。

常见参考：

- 通用模板：`page-data-load-template.md`
- 直连查询：`LSRefundSerialController.loadLSRefundSerials.do`
- 单据引擎：`VoucherController.loadPay.do`

## 可复制模板

如果你换到别的项目，优先先看 [page-data-load-template.md](page-data-load-template.md)。  
那份模板用的是中性命名和通用结构，不依赖某个省份项目。

## 方案一：直连查询

### 适合

- 新加表。
- 产品化里没有对应 billType 配置。
- 你只想把查询跑通。
- 页面只是普通列表查询、筛选、分页、导出前查询。

### 需要做什么

- 先参考同项目已有 `loadXXX.do` 接口。
- Controller 负责接收参数、构造查询条件、分页。
- Service/DAO 负责拼查询、查表、组返回结果。
- 返回结构要和前端现有 `buildPageResult`、`JsonUtil.getListViewPaging` 或项目既有格式一致。
- 字段名、排序、默认条件要跟前端约定一致。

### 优点

- 最直接，改动小。
- 不依赖 billType、字段映射、明细配置。
- 出错面更窄，适合你日常新表新页面。

### 注意点

- 参数名要和前端一致。
- 分页、排序、空值条件要和现有页面保持一致。
- 如果返回字段需要格式化，优先在后端统一处理。

## 方案二：单据引擎

### 适合

- 业务本身已经走 billEngine 体系。
- 目标页面必须纳入统一单据生命周期。
- 你愿意额外维护 billType、字段映射、明细配置。

### 需要做什么

- 新增或确认 billType。
- 配置主表字段映射。
- 配置明细表字段映射。
- 配置加载、更新、删除相关的单据关系。
- 页面接口改为按 billEngine 的装载方式取数。

### 优点

- 和现有单据体系统一。
- 后续如果同类业务很多，复用性更强。

### 缺点

- 配置多，前置条件多。
- 产品化里没有现成配置时，落地成本高。
- 容易漏字段映射或明细配置。

## 推荐方案

默认推荐**直连查询**。

原因：

- 你当前的常见任务是“新加页面 + 新表 + 让列表能查出来”。
- 这类需求的核心是快速、稳定地加载数据，不是重建单据体系。
- 单据引擎更像业务平台能力，不适合作为新增页面的默认路径。

只有当目标项目已经明确要求纳入单据引擎，或者现有同类页面就是这么做的，才走单据引擎。

## 实施清单

- 先找同模块最接近的 `loadXXX.do`。
- 确认前端传参名称、分页参数、字段列表参数。
- 确认返回格式是否需要 `ReturnPage`、`buildPageResult` 或直接 JSON。
- 直连查询时，优先复用现有查询封装，不要硬拼字符串。
- 单据引擎时，先确认 billType、字段映射、明细配置都已准备好。
- 不要把页面配置 SQL 和数据加载逻辑混成一份模板。

## 与 SQL 的关系

页面配置 SQL 仍然只管：

- 菜单
- 模块
- 按钮
- 状态
- 列字段

`loadXXX.do` 的查询逻辑不属于 SQL 模板，应该按后端接口和查询场景单独处理。
