# 需求讨论流程

## 核心原则

**编码前充分讨论，确保需求理解一致**

在用户明确说"开始"之前，不进行任何编码工作。通过结构化的讨论确保双方对需求理解一致。

## 讨论流程

### 阶段一：需求理解与澄清

1. **阅读需求文档**
   - 仔细阅读用户提供的所有需求文档
   - 识别关键业务概念和术语
   - 理解业务背景和目标

2. **提出澄清问题**
   - 需求中模糊或矛盾的地方
   - 边界条件和异常情况
   - 数据来源和流向
   - 与现有系统的关联关系

3. **确认关键点**
   - 列出自己理解的关键点，请用户确认
   - 使用"我的理解是...，请确认是否正确"的句式

### 阶段二：方案分析

1. **提出多种实现方案**
   - 至少提出2-3种可行方案
   - 每个方案说明核心思路

2. **对比分析**
   - 每个方案的优点
   - 每个方案的缺点
   - 适用场景

3. **给出推荐方案**
   - 明确推荐哪个方案
   - 说明推荐理由

### 阶段三：技术细节确认

1. **数据库设计**
   - 需要新建哪些表
   - 表结构设计
   - 索引设计

2. **接口设计**
   - 需要调用哪些外部接口
   - 需要提供哪些接口

3. **页面设计**
   - 页面功能布局
   - 交互流程

### 阶段四：风险识别

1. **技术风险**
   - 性能瓶颈
   - 并发问题
   - 异常处理

2. **业务风险**
   - 数据一致性
   - 业务规则冲突

## 输出格式

讨论过程中使用以下格式组织信息：

```markdown
## 需求理解

### 关键业务点
- 点1
- 点2

### 待澄清问题
1. 问题1？
2. 问题2？

## 实现方案

### 方案一：xxx
**核心思路**：...
**优点**：...
**缺点**：...

### 方案二：xxx
**核心思路**：...
**优点**：...
**缺点**：...

### 推荐方案
推荐方案X，理由：...

## 技术设计

### 数据库设计
...

### 接口设计
...

## 风险点
1. 风险1及应对措施
2. 风险2及应对措施
```

## 注意事项

- 保持耐心，不要催促用户
- 鼓励用户提出自己的想法
- 当用户说"开始"或"可以开始编码了"时，才进入编码阶段
- 讨论过程中可以参考现有代码来辅助理解
